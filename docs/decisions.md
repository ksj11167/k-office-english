# K-직장인 영어 — 결정 기록

메신저 대화 로그를 학습 소스로 삼는 영어 말하기 앱. 이 문서는 `/deep-interview`
9라운드와 그 뒤 사용자 지시로 확정된 내용을 담는다.

- 인터뷰 종료 시점 모호도: **23.5%** (목표 10% 미달). 이후 D18~D25로 상당수가
  정해졌고, 남은 것은 아래 "미해결" 표에 있다 — 대부분 **실사용 없이는 못 정하는 값**이다
- 상태: **공개 배포 중** · 테스트 75개 · Android·iOS 빌드 CI 통과
- 앱: `app/` · 소개: `site/` · 백엔드: `server/`(번역 프록시, 코드 완료·미배포)
- 배포: GitHub Pages · Claude 아티팩트 · Capacitor(Android 먼저, iOS는 D21)

---

## 확정된 결정

| # | 결정 | 근거 |
|---|---|---|
| D1 | 학습 단위는 **하루치 대화** | 6개월 일괄 처리 시 카드 3,000장 → 150일. 시간축으로 끊으면 분량 문제가 구조적으로 사라지고, 번역 비용도 세션당 ~$0.01로 떨어진다 |
| D2 | 카드 앞면 = **내 한국어 원문 그대로** | 빈도·난이도 선별 없음. 사용자가 2회 재확인: 맥락에서 뜯겨나온 표현 목록보다 대화 순서 그대로가 일화적 기억에 유리 |
| D3 | 카드 뒷면 = **자연스러운 구어 영어 1개** | 후보 나열 없음. 지시어("그거")는 영어에서도 that/this로 보존 |
| D4 | 성공 기준 = **실제로 입에서 나옴** (전이) | 재인이 아닌 인출. 카드는 production 방향(한국어→영어 말하기) |
| D5 | 수집 = 카톡 **대화 내보내기 .txt** | 카카오 공식 API는 송신·공유 전용. 대화 읽기 API 없음 |
| D6 | 파싱 후 **미리보기 승인 게이트** | 파싱은 반드시 어디선가 틀린다. 근거가 둘이었는데(비용 절약·오류 발견) 앞엣것은 D18로 소멸했고 뒤엣것은 유효하다. 틀린 걸 번역해봐야 쓰레기가 나온다. 근거가 둘이었는데(비용 절약·오류 발견) 앞엣것은 D18로 소멸했고 뒤엣것은 유효하다 |
| D7 | **상대방 발화도 수집** | 사용자 지시로 D7-old(내 발화만) 역전. 맥락이 있어야 "그거"가 해석되고 번역 품질이 산다 |
| D8 | 플랫폼 = **웹앱(PWA)** | 심사 없이 즉시 배포. iOS는 공유시트 수신 불가(Web Share Target 미지원)라 "파일 저장 → 앱에서 선택" 한 단계 추가 |
| D9 | 채점 = **음성인식 + 자가판정 폴백** | 스픽 스타일 요구 반영. Web Speech API, 미지원 브라우저는 자가판정으로 degrade |
| D10 | AI 롤플레이는 **2단계** | MVP 제외. 비용이 아니라 구현 난이도가 결정 요인. D18 확정 후 재확인 — 재료(영어로 옮겨진 상대방 턴)는 v1에서 준비되므로, 2단계는 화면을 붙이는 일이 된다. D18 확정 후 재확인 — 재료(영어로 옮겨진 상대방 턴)는 v1에서 준비되므로 2단계는 화면을 붙이는 일이 된다 |
| D11 | 채점 입력은 **스와이프** | 데이팅 앱 제스처 차용. 오른쪽 "외웠다", 왼쪽 "다시". 수십 번 반복하는 이진 판단이라 엄지 한 번이 버튼 찾기보다 빠르고, 드래그 중 판정이 미리 보인다. 버튼·화살표키로도 동일하게 접근 가능 |
| D12 | 스케줄러는 **FSRS** (`ts-fsrs`, MIT) | 직접 짠 SM-2 대체. 카드별 기억 안정성·난이도를 모델링해서, 계속 틀리는 카드가 덱 전체를 끌고 가지 않는다 |
| D13 | 배포는 **GitHub Pages + Claude 아티팩트 양쪽** | 같은 코드. Pages는 설치형 PWA(본인 API 키), 아티팩트는 키 없이 `claude.use("sample")` |
| D14 | 맥락은 **날짜 경계를 넘지 않는다** | 금요일 마지막 말은 일요일 첫 말의 맥락이 아니다. 실제 화면에서 발견한 버그를 고치며 확정 |
| D15 | 포지셔닝은 **K-직장인 생활 영어** | "영어회화 앱"은 레드오션. "회사에서 매일 쓰는 그 말"은 타겟이 좁아지는 게 아니라 날카로워지는 것. 앱 이름도 «K-직장인 영어»로 교체 |
| D16 | 공유 단위는 **대화가 아니라 카드** | 대화 공유 = 동의 없는 동료 발화의 제3자 제공. 문장 쌍 + 상황 태그만 공유하면 안전하고, 남의 사생활 대신 «직무별 표현집»이 되어 더 유용하다 |
| D17 | 공유 1단계는 **앱 내장 직무 덱** | 사용자가 없는데 백엔드부터 세우면 서버 비용과 개인정보 책임만 먼저 생긴다. 내장 덱으로 "공유받는 쪽" 가치를 먼저 검증하고, 기여(2단계)는 그 다음. **D20으로 v1에서 빠짐** |
| D18 | 번역 범위는 **그 날 대화 전체** | D7(상대방 발화도 수집)에서 한 걸음 더. 상대방 발화까지 영어로 옮겨야 「내 차례만 비어 있는 영어 대화」가 만들어지고, 그게 롤플레이(D10)가 성립하는 유일한 재료다. 부수 효과로 입력 토큰이 줄어든다 — 지금은 한 메시지가 뒤따르는 발화들의 맥락으로 여러 번 전송되는데, 하루치를 통째로 보내면 한 번씩만 들어간다 |
| D19 | 「나 고르기」는 **번역 뒤로** | 지금 순서(번역 전)의 이유는 비용 게이트였다 — 내 발화만 번역하니 누가 나인지 먼저 알아야 했다. D18이 그 제약을 없앴다 |
| D20 | 직무별 표현집은 **v1에서 빠지고 추후 마일스톤** | 앱이 하는 일을 두 가지(전체 번역·카드)로 좁히기로 함. 코드와 200장은 남기되 v1 화면에서는 내린다. **대가: 번역 없이 돌아가는 유일한 경로가 사라져 번역 서버가 v1의 진입 조건이 된다** |
| D21 | **Android 먼저 출시, iOS는 그 다음** | ~~Mac 없이는 iOS를 폰에 올릴 방법이 없다~~ — **틀린 근거였다 (2026-09-16 정정).** 레포를 공개로 돌린 뒤 macOS 러너가 무료·무제한이 됐고, App Store Connect API 키로 CI에서 서명·TestFlight 업로드까지 된다. 실제 장벽은 하드웨어가 아니라 Apple $99/년과 서명 설정이다. 그래도 Android가 먼저인 이유는 $25 한 번에 끝나고 설정이 훨씬 간단해서다 |
| D22 | 레포를 **공개**로 전환 | GitHub Pages가 열려 처리방침 공개 주소와 테스터 링크가 한 번에 해결된다. 소스에 키·개인정보는 없다 (키는 Cloudflare secret, 대화는 기기 안) |
| D23 | 앱 ID는 **com.ksj11167.kofficeenglish** | 옛 이름 realtalkenglish를 버렸다. 출시 후에는 영원히 못 바꾸므로 출시 전인 지금 정리 |
| D24 | 영어 문장 **읽어주기** | 테스터 요청. 앱은 사람에게 한 번도 들어본 적 없는 문장을 말하라고 시킨다. 눈으로 읽으면 단어는 알아도 소리의 모양은 모른다. `speechSynthesis`라 웹·PWA·WebView 전부에서 되고 플러그인이 필요 없다 |
| D25 | PWA도 **공유 대상**으로 등록 | 테스터 요청 — 매번 내보내기가 번거롭다. 네이티브 셸은 이미 공유시트로 받고 있었지만 설치형 PWA는 못 받았다. Android에서 웹으로 쓰는 사람에게는 이게 유일한 개선 경로다. **iOS Safari는 여전히 불가** |

### 배제한 것

- **알림 접근 권한 상시 수집** — 상대방 동의 없는 수집에 가깝고 스토어 정책·약관 리스크
- **카톡 로컬 DB 직접 읽기** — 리버스 엔지니어링, 약관 위반, 업데이트마다 파손
- **캡쳐 + OCR** — 발화자·타임스탬프 부정확, 분량 한계. 내보내기가 되는데 쓸 이유 없음

## 미해결 (모호도 23.5%가 남은 이유)

10% 목표를 채우려면 Constraints·Criteria가 전 컴포넌트에서 0.90이어야 한다.
사용자가 취침 전 "프로토타입까지" 지시하여 아래는 **내가 가정으로 채웠다.**

| 항목 | 가정한 값 | 확인 필요 |
|---|---|---|
| 플랫폼 | 웹앱(PWA) + Capacitor | 해결 — 양쪽 네이티브 빌드가 CI에서 통과 (2026-09-16) |
| 오프라인 동작 | 번역만 온라인, 복습은 오프라인 | 미논의 |
| 기기 간 동기화 | 없음 (localStorage, 브라우저별) | 미논의 — `db` 도입 시 해결 |
| 음성 채점 임계값 | 토큰 일치 70% | 임의값. 실사용 튜닝 필요 |
| 스와이프 확정 거리 | 140px 또는 빠른 플릭 | 임의값. 손 크기·기기별 튜닝 여지 |
| 하루 세션 분량 | 그 날 전부 + 이전 날짜 복습 최대 8장 | 임의값 |
| 번역 모델 | `modelTier: "default"` | quick으로 낮출 여지 |

### 알려진 리스크

- **iOS Safari PWA는 공유 대상 등록 불가** → 카톡에서 바로 앱으로 못 보냄
- **Chrome 음성인식은 오디오를 구글 클라우드로 전송** → D7 완화 전의 온디바이스 원칙과 긴장. 현재는 상대방 발화도 보내기로 했으므로 일관성 문제는 줄었으나, 음성은 여전히 제3자 경유
- **카톡 내보내기 포맷은 고정 계약이 아님** — 카톡 업데이트로 깨질 수 있음. 파서 테스트가 회귀 방어선
- `developers.kakao.com` 접근이 막혀 **카카오 API 제약을 공식 문서로 최종 확인하지 못함**
